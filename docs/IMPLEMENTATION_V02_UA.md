## Дані та FAQ

Руйнівних змін SQLite для 0.2 немає. Наявна схема й сумісні міграції
зберігають звернення, контакти, меню, чернетки, стан користувачів і призначення.

Одноразова міграція `content_v02` оновлює типові Q01–Q08.
У змінених карток попередня публікація й чернетка збережені в тому самому записі;
погоджена основа 0.2 використовується для актуальної публікації. Видалені раніше
FAQ не відновлюються. Інші попередні відповіді збережені для редагування,
але потребують погодження щодо 0.2 перед публікацією. Нові FAQ редактора мають
робочий шлях чернетка → попередній перегляд → затвердження → публікація.
Ліміт 68 дозволяє мігрувати повний попередній каталог із 60 записів плюс 8 карток.
За помилки запису файла міграція не змінює диск або стан пам’яті й допускає повтор.

Немає другого незалежного джерела відповідей: після міграції чинні FAQ
редагуються в одному каталозі. `faq_v01.json` використовується тільки як база
порівняння. Q01 має окрему дату й може оновлюватися незалежно.

## Локальна перевірка

З кореня репозиторію виконайте автономні тести. Інтерфейс Linux із Tkinter:
`./START_LINUX.sh` або `python3 main.py`. Повний ручний сценарій і створення
окремої тестової копії — `MANUAL_CHECK.md`. Після оновлення зупиніть раніше
запущений процес бота й запустіть його знову, щоб завантажити каталог 0.2.

Короткий сценарій: `/start` → напрям → співфінансування → умови → меню →
підрозділи/FAQ/помічник → підтримка → контакти → окреме поле → перевірка →
надсилання → прийняття спеціалістом → діалог → завершення → повернення.
Окремо перевірте Q02/Q03, B03/B04, A05/Q08, перезапуск, іншого клієнта та FAQ-міграцію.

## Git і підпис

Гілка: `feature/content-v0-2`, на основі поточної реалізації 0.1.
Кодовий коміт `413a757` — «Оновлено навігацію й нормативний каталог до редакції 0.2».
Він уже відправлений до `origin/feature/content-v0-2`; upstream налаштований.
Документація оформлюється окремим логічним комітом; його хеш і остаточний
результат push наведено у фінальному повідомленні.

У конфігурації Git підпис не ввімкнений і ключ не заданий. Попередня спроба GPG
завершилася `No secret key`. Використано раніше наданий дозвіл на коміти без
підпису; налаштування Git не змінювали. Виконується звичайний push робочої гілки
до наявного origin, без merge в основну гілку, зміни адреси або force push.
